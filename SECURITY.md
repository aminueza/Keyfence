# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository
(Security tab, "Report a vulnerability"). Do not open a public issue for a
security problem. You will get an acknowledgement within a few days and a
fix or a documented decision before any public disclosure.

## What keyfence sees and stores

keyfence is a man-in-the-middle proxy for the hosts it monitors. It reads
the full body of every request to those hosts and, in `placeholder` mode,
the full response. This is the point of the tool, and it is also why it
runs only on your machine, listens only on 127.0.0.1 by default, and never
sends anything anywhere except to the provider you were already talking
to.

On disk it keeps:

- `~/.keyfence/vault.json`: salted HMAC-SHA256 hashes of your secrets, never
  the values, mode 0600.
- `~/.keyfence/audit.log`: one line per request with findings, with a masked
  preview (first and last four characters) and the JSON key, never the
  value.
- `~/.keyfence/env/`: the environment snapshot of a running `keyfence exec`,
  hashes only, deleted by the proxy at startup.
- `~/.mitmproxy/`: the CA certificate and key generated by mitmproxy. Anyone
  who can read that key can intercept TLS on this machine for any client
  that trusts the CA. Protect it like an SSH key.

The `notice` feature appends a short text to the system prompt of requests
it changed. That is the only content keyfence adds to a request.

## Threat model

In scope: accidental leakage of secrets through prompts, tool results and
files that coding agents send to LLM providers. keyfence is a last line of
defence and works best with the Claude Code hook that stops the files from
being read at all.

Out of scope: a program that deliberately hides secrets (encoding,
splitting, encryption), certificate-pinning clients, traffic that bypasses
the proxy, and secrets in headers or query strings, which are left alone
because they usually carry the provider's own key. See
[docs/limitations.md](docs/limitations.md).

## Supply chain

- Releases are built and published by the `Release` GitHub Actions workflow
  through PyPI trusted publishing. No long-lived token exists. PyPI records
  a provenance attestation for every file, linking it to the workflow run
  and commit; it is shown on the PyPI file listing and can be checked with
  `pypi-attestations`.
- CI builds a CycloneDX SBOM for every commit on `main` and every pull
  request; it is attached to the workflow run as an artifact.
- Dependencies are `mitmproxy` and `PyYAML`, both from PyPI. The bundled
  detection rules come from the gitleaks repository and are checked in, so
  nothing is fetched at runtime.
- Tests run on Linux, macOS and Windows.

## Design choices that limit blast radius

- A detector exception fails closed: the request gets a 403.
- A corrupted vault stops the proxy at startup with a message and makes a
  running proxy fail closed until it is fixed.
- An empty or missing config file does not change a running proxy.
- `keyfence run` replaces its own process with mitmproxy, so killing it
  cannot leave a proxy behind.
